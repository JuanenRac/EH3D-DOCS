# Architecture

The suite is a set of independent programs that share two libraries and one project file. The programs are written in Rust; the tools around them (the updater, the repository checks) are Python.

## Layers

1. **[EH3D-COMMON](https://github.com/JuanenRac/EH3D-COMMON)** defines what every program agrees on: the `.eh3dproj` container (a ZIP archive with `project.json`, `integrity.json`, `layers/`, `toolpaths/` and `vision/`), the telemetry types of a machine and the colours of the suite. It depends on nothing of the suite. The same repository holds the crates that the programs of the suite share: `eh3d-view` (the scene of a job, the themes and the words of the interface in the eight languages), `eh3d-archive` (jobs in ZIP archives), `eh3d-bungard-formats` (the files of the Bungard machines and the Gerber and DXF outlines), `eh3d-controller` (the interface of the machine controllers), `eh3d-filedialog` (the Open and Save windows), `eh3d-summary` (the dry run of the exact plan of a job and the summary before a start, so the programs, the modern interface and the server say the same), `eh3d-image` (the reader of PGM and PNG pictures, with limits so that a hostile file cannot ask for gigabytes), `eh3d-diagnostic` (a diagnostic with a stable code, severity, category and place), `eh3d-container` (what every container format shares: the integrity record, the entry-name rule and canonical JSON; `.eh3dproj` 1.0.0 is a preset of it) and `eh3d-materials` (the database of board materials, 723 of them with the file each value comes from, and the catalogue of 1873 reference documents classified for a CNC and for the design tool; it opens no window, no file and no network). The reference packages of the container are tests that fix its behaviour byte for byte.
2. **[EH3D-CORE-LIBS](https://github.com/JuanenRac/EH3D-CORE-LIBS)** reads the files that other people send (Gerber, Excellon, G-code). It depends on nothing but the standard library and has no window. It also holds the crates that the CAM programs share instead of keeping a copy each: `eh3d-raster` (units of length, the exact distance transform of a grid and its contour lines), `eh3d-geometry` (the shapes of a layer and the conversion of Gerber and Excellon into them) and `eh3d-cam` (isolation, forced and fill passes, checks of gaps and tolerances, the order of paths, fiducials and board transforms), and the writers of Gerber (X2) and Excellon, which give the same bytes for the same content. The plan to end the two pairs of readers of Gerber and Excellon is in `docs/UNIFICATION.md` of that repository and is not done.
3. **The programs** (CAM, viewers, machine control, the launcher) are meant to depend on the two libraries and never on each other: they exchange work through project files: `.eh3dproj` (the job of a machine) and `.eh3d` (the whole project, with a branch for each program; see [PROJECT_FILE.md](PROJECT_FILE.md)). The programs that have started (EH3D-GERBERVIEWER, EH3D-ISOCAM, EH3D-STENCILCAM, EH3D-CAM-DEBUGGER, EH3D-PHOENIX-LASER, EH3D-AUTOLEVEL, EH3D-PHOENIX-PNP, EH3D-VISION-STUDIO, EH3D-TOOL-MANAGER and EH3D-SUITE-LAUNCHER) are a library and a command line each, tested on a computer, and use the readers of EH3D-CORE-LIBS or the height map of EH3D-COMMON; EH3D-GERBERVIEWER, EH3D-ISOCAM, EH3D-STENCILCAM and EH3D-PHOENIX-PNP also have a window (egui, built with `--features gui`) whose logic is plain code tested without a screen, and the Windows executables of these four, of EH3D-PHOENIX-CNC, EH3D-BUNGARD-GUI, EH3D-DRILLPRO and EH3D-ROUTEPRO carry the icon of the program; EH3D-PHOENIX-PNP is the planner and the simulator of the placement of parts; EH3D-ISOCAM also uses the shapes of EH3D-GERBERVIEWER. EH3D-SUITE-LAUNCHER finds every program by its manifest and starts it. Today EH3D-DRILLPRO, EH3D-ROUTEPRO and EH3D-BUNGARD-GUI read their files with `eh3d-bungard-formats`, ROUTEPRO reuses the protocol and the screens of DRILLPRO, and EH3D-BUNGARD-GUI and EH3D-PHOENIX-CNC draw their windows with the crates of EH3D-COMMON (themes, words, file windows). EH3D-DRILLPRO, EH3D-ROUTEPRO and EH3D-PHOENIX-CNC can send their work to EH3D-SERVER instead of to a machine, and read its answer with `eh3d-fleet`.
4. **The machines.** **[EH3D-NODE-BUNGARD](https://github.com/JuanenRac/EH3D-NODE-BUNGARD)** is an ESP32-S3 node that sits in the box of a Bungard CCD machine and puts its serial port on the network; the firmware that every node shares is kept in EH3D-COMMON (`firmware_base/`). **[EH3D-SERVER](https://github.com/JuanenRac/EH3D-SERVER)** is the center: it takes the jobs of the programs and of the clients to come, plans them with the libraries of the programs and runs them on the machine through its node. It also knows the spindle that each machine carries (the original one, 63000 rpm, or the one with a variable-frequency drive, 24000 rpm) and refuses a job beyond its limits unless a safety switch is set to warn; a job can be a drilling and a routing one after the other, each with its tools switched off. A job can also be a free G-code program (`kind` `gcode`): the server cleans it, judges it against the spindle and runs it line by line on the simulator or on a GRBL controller on a serial port of its own computer (`connection` `grbl`), where it can be held and resumed and gone on from the line where it stopped; a node takes drilling and routing, a GRBL controller takes G-code, and the simulator takes all three. A job that goes on after a stop waits for a person: apart before the spindle or the laser goes on and, on a machine not said to carry a laser, before the tool goes down into the work; an answer can name the question it answers, so an old screen does not answer a new one. A drill file that does not declare how its numbers are written is not planned by supposing it: the request names the format (`drill_format`).
   **[EH3D-NODE-BUNGARD-AUX](https://github.com/JuanenRac/EH3D-NODE-BUNGARD-AUX)** sits on the drill head: it measures the height of the table with a laser, watches the speed and the temperature of the spindle (several temperature sensors on one wire, a reflective sensor for the speed) and sends the camera like an IP camera (RTSP and ONVIF); the programs use its measures to build the height map of the table (`eh3d-levelling` of EH3D-COMMON) and correct the Z of the jobs; they reach it directly or through EH3D-SERVER, which relays its status, its camera and its measure with the token it holds.
5. **The phone apps** [EH3D-ANDROID-CONTROL](https://github.com/JuanenRac/EH3D-ANDROID-CONTROL) and [EH3D-IOS-CONTROL](https://github.com/JuanenRac/EH3D-IOS-CONTROL) are clients of EH3D-SERVER only: they read the fleet, the jobs and the node of the drill head through its API with the token of a person, prepare drilling, routing and G-code jobs, hold and resume a G-code job, go on from a stopped job with the request that the server kept, read the switch of the `$` lines of GRBL of a machine, and the emergency stop is the cancel of the running job; they do not talk to a machine or a node. EH3D-STUDIO, the web panel the server serves, is the other client: it sets up the machines (a node, the simulator or a GRBL controller), prepares and follows the jobs, goes on from a stopped job without asking for the file again, lets an administrator allow the `$` lines of GRBL per machine, and shows the node of the drill head.
6. **The touch screens:** [EH3D-NODE-BUNGARD-HMI](https://github.com/JuanenRac/EH3D-NODE-BUNGARD-HMI) (the Bungard machine) and [EH3D-NODE-HMI-GUI](https://github.com/JuanenRac/EH3D-NODE-HMI-GUI) (its general purpose copy for CNC, laser and pick and place machines, where only a CNC machine gets the spindle button and the quality check) are ESP32-P4 screens (in the eight languages of the suite) whose rules, in a core tested on a computer, put every move through one gate with confirmation and a hardware-stop latch.
7. **The updates.** The CM5 is updated from the releases of GitHub by a helper that checks the SHA-256 of every package and, when the machine has a file of allowed signers, installs only a package signed with the key of releases; a development PC is updated by the Updater; the modern interface can update itself on request. See [UPDATING.md](UPDATING.md).
8. **[EH3D-UPDATER](https://github.com/JuanenRac/EH3D-UPDATER)** installs and updates the repositories on the PC of the person using them. **[ELECTRO-HOBBY-3D-UPDATER](https://github.com/JuanenRac/ELECTRO-HOBBY-3D-UPDATER)** sits above the updaters of the four ecosystems and dispatches to the one the person picks.
9. **The PHOENIX project** (electronic design) is a family of repositories that reuse the same base: [EH3D-PHOENIX-PCB](https://github.com/JuanenRac/EH3D-PHOENIX-PCB) (the main project, with a first release; a workspace of crates behind one command, `phoenix`: the model, the project file, EAGLE files, connectivity and rules, stack-up and impedance, RF tools and the manufacturing export), [EH3D-PHOENIX-CAD](https://github.com/JuanenRac/EH3D-PHOENIX-CAD) (parametric enclosures with expressions for the parameters, special holes and edges, mass properties and the fit check against a board; a first release, a library without a window), [EH3D-VALIDATION-LAB](https://github.com/JuanenRac/EH3D-VALIDATION-LAB) (golden sets, results with classes and a gate against a baseline), eight early libraries and tools with a first release, each a library with a command line (the verifier, manufacturing profiles, the history of a design, the project passport, a component database, thermal simulation, the bridge to laboratory measurements and the explorer of alternatives) and one that is only planned (the adapter to HYDRA-UMC). They share the container and the diagnostic of EH3D-COMMON (the stack-up of PHOENIX-PCB can take its materials from `eh3d-materials` once that crate is released) and have their own registry of codes; see [CONVENTIONS.md](CONVENTIONS.md).

## What the layers share beyond the container

* **The docking frame.** `eh3d-dock` (EH3D-COMMON) gives every desktop program the panels that can be moved, tabbed, floated, folded and locked, the workspaces and the menu bar declared as data, with the layout kept in the configuration file of the program. See [DOCKING.md](DOCKING.md). The PHOENIX programs also take from it their colour, their About window and their recent projects ([PHOENIX_FAMILY.md](PHOENIX_FAMILY.md)).
* **Shared databases.** `eh3d-materials` (board laminates) and `eh3d-printmaterials` (filaments and resins) live once in COMMON and are read by the design tool, the machine programs, the slicer and the server. A program looks in COMMON and CORE-LIBS before it makes a table of its own. See [MATERIALS_DATA.md](MATERIALS_DATA.md).
* **The client of the server.** `eh3d-serverclient` (EH3D-COMMON) is the one client the Rust programs use: login with the application they are, renewal of the session, the queue of requests that could not be sent, the project store with its tags and the sentence of every error code in eight languages.
* **The contract of the settings.** EH3D-SERVER publishes `docs/settings-contract.json` (every setting and switch, its range, default, risk and words in eight languages), the error codes and the OpenAPI document. The clients draw their settings pages from the contract and keep a guard that fails when they fall behind; EH3D-STUDIO, the phone apps and the touch screens draw them; the programs of the machines are to follow. See [CLIENT_SYNC.md](CLIENT_SYNC.md) and [ERROR_CODES.md](ERROR_CODES.md).
* **The firmware base of the nodes.** The part of the firmware that every node needs (settings in flash, users and sessions, the network, the update with rollback, the guard of tasks and memory) is kept once in `firmware_base/` of COMMON and copied into each node by a tool that checks the copies. The projects are in groups (the ESP32-S3 nodes, the ESP32-P4 touch screens) and a group receives what is imported from one of its members; `--only` takes just some files of a group. A change of the base goes to COMMON and to every node of the group in the same batch.
* **One reader for Gerber and Excellon, and the 2D geometry.** EH3D-CORE-LIBS holds the reader the other programs move to (with a corpus of boards and snapshots as the safety net) and `eh3d-geometry` (shapes, offset, boolean operations, arcs). See [GERBER_MIGRATION.md](GERBER_MIGRATION.md).
* **The formats of the design family.** EH3D-PHOENIX-PCB reads the interchange format IPC-2581 (revisions A, B and C) and EAGLE files, checks a board against the rules of a fabricator (profiles of the known fabricators, kept as data with `verified: false` until compared with the real rules) and checks the design from the Gerber files themselves.
* **The chain of release and binaries.** What is compiled and signed is the tip of main; the binaries are built in GitHub Actions, downloaded and signed on the maintainer's machine, and published with their checksums and signatures. See [RELEASE_CHAIN.md](RELEASE_CHAIN.md).

## Rules

* **A reader never panics and never guesses.** What cannot be understood becomes a diagnostic with a stable code and the number of the line.
* **A package is trusted by its hash and, where the machine asks for it, by its signature:** the hash says the file arrived whole, the signature says who made it.
* **A file from outside is hostile until proven otherwise:** sizes, entry names and number formats are checked before they are used.
* **A program does not decide that a G-code is safe to run.** Limits, interlocks and the emergency stop belong to the machine and its controller.
* **Every repository describes itself** with an `eh3d.project.json` manifest; nothing keeps a list of projects, so a new repository appears by having a manifest.
* **Texts exist in eight languages** wherever a repository shows text to people (README files and texts of the interfaces); these eight and no others, the drilling and routing programs included.
* **Every behaviour has a test**, including the refusals.
* **Every option of security is a switch that can be seen** in the studio and in every client, and its default is the conservative one. When something goes wrong, a program goes towards what is safer, never towards what is looser ([DESIGN_RULES.md](DESIGN_RULES.md)).
* **Evidence is declared.** A capability is `simulator`, `bench` or `field`; nothing is called working on hardware that has not run on hardware.
* **A tuned parameter lives in a configuration file,** never in the code, and a table of data lives once in COMMON.
* **Every repository carries the same five documents** (scope, requirements, status, what is not yet and the rules for changing it): see [DOCS_TEMPLATE.md](DOCS_TEMPLATE.md).
