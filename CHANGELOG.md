# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The text of the banner is checked against the manifest:** `tools/banner_check.py` (called by `ci_validate.py`) compares the tag, the title, the line of technologies, the pills and the badge of `images/*BANNER*.svg` with the role, the name and the technologies of the manifest, so a banner copied from another repository is found; the plain banner of a new repository is checked for its name.
- **The scan for forbidden words reads what git tracks:** `ci_validate.py` (tools version 2) takes the file list from `git ls-files`, so `.venv`, `node_modules` or `dist` never give a false alarm and a local run says what CI says; outside a git checkout it reads every file.
- **Where the shared tools come from:** `docs/vendored.lock` records the origin and the digest of every shared tool, `sync_shared_tools.py --lock` writes it and `--check` fails when a canonical copy changed without it.
- **The version bump follows more places:** `bump_version.py` also raises the internal dependencies that ask for a minimum version (`version = ">=..."` on a package of the same repository), the `Cargo.lock` entries of the members of a workspace that inherit the version, and the manifest of the updater of the whole family (`electro-hobby-3d.project.json`).
- **Exit codes of the Rust programs, written down:** `docs/CONVENTIONS.md` says what each program ends with today and which code each case takes when the program adopts the table; no program is changed.
- **The report of vendored tools nobody uses is regenerated:** three checks that nothing ran were removed from three repositories.
- **The maturity is functional:** the manifest, the badge and the table of the eight README files say it, since it is used and tried with real files; the evidence stays as host tests.
## [0.0.5] - The suite map and the guides up to the published versions

- **The README files in the eight languages are up to date with the tools:** the tools, the suite contract with its checks, the version and release scripts, the reusable workflow, `bootstrap_workspace.py`, `new_repo.py` and `docs/suite.json` are in the overview, the status table (with lights that say the release and workspace scripts have only been tried on toy repositories), the interfaces, the configuration, the quick start, the testing section, the limits and the file tree; the test count is the real one and the Architecture and Repository Structure pictures are drawn again.
- **The issue forms and the pull-request template are checked:** the new `templates` check of `tools/suite_contract.py` warns about every repository (and the Updater of the whole family) that lacks one of the files that `docs/suite.json` lists in `github_templates`; this repository, EH3D-UPDATER and ELECTRO-HOBBY-3D-UPDATER have all of them.
- **A script that makes the folder of a new repository:** `python -I tools/new_repo.py EH3D-NAME --dest DIR` writes the base every repository has from the template in `docs/templates/new_repo/` (manifest, the eight README files in the universal layout with honest status lights, changelog, licence, community files, CI workflow, issue forms and pull-request template, the shared tools of this hub, a test of the base and the data and pictures of Architecture and Repository Structure) and runs the checks of the suite on the result; it does not run git and refuses a folder that exists.
- **A script to set up a workspace from one repository:** `python -I tools/bootstrap_workspace.py --workspace DIR REPOSITORY` lists the repositories that one needs next to it, following the `path = "../EH3D-X"` of every `Cargo.toml`, the `file:`, `link:` and `portal:` references of every `package.json` and the `depends_on` of the manifest, recursively and with no list of repositories; it changes nothing unless `--clone` is given, which fetches the missing ones with `git clone --depth 1`.
- **Naming conventions, written and not enforced by renaming:** `docs/CONVENTIONS.md` has a table of the names of repositories, packages, executables, services, tags, branches, configuration files and README files as they are today, and documents the optional `binary` field of the manifest (the file name of the executable a repository builds), which the parser of EH3D-UPDATER now accepts.
- **A convention for the exit codes of the command-line tools:** `docs/CONVENTIONS.md` gives 0 (done), 1 (failed), 2 (done with warnings), 10 (something to do) and 64 (wrong use); `python -I tools/exit_conventions.py` checks the scripts of `tools/` against it, the tools of this hub now end a wrong option with 64 (`UsageParser`), and the differences of the shared copies and of other repositories are written down, not changed.
- **The constants of the suite in one file:** `docs/suite.json` holds what several repositories repeat (the port of the server, the manifest name and schema versions, the eight README languages with their codes, the rpm field of the panel and the shape of a version), and the new `constants` check of `tools/suite_contract.py` compares them with the places that repeat them; it only warns.
- **A guide to raising a version and publishing a release:** `docs/RELEASING.md` explains the odometer and the steps with the scripts of `tools/` (`bump_version.py`, `prerelease_check.py`, `release_notes.py`, and the two reports), with the exact commands, what each one checks and what none of them does.
- **The common validation as a reusable workflow, not adopted yet:** `.github/workflows/validate.yml` (`on: workflow_call`) runs `ci_validate.py` and the checks of the README pictures of the calling repository, with the inputs `python-version`, `check-pictures`, `check-links` and `run-tool-tests`; `docs/REUSABLE_VALIDATION.md` explains the inputs, how a repository calls it (`uses: JuanenRac/EH3D-DOCS/.github/workflows/validate.yml@<tag>`) and how to try it in one pilot repository first. No repository calls it yet. A test keeps the workflow, its inputs and the guide in agreement.
- **A report of the vendored tools that nothing uses:** `python tools/vendored_tools_report.py --write docs/VENDORED_TOOLS_REPORT.md` reads the `tools/` folder of each repository next to this one and lists the scripts that no workflow, no run / build / test script, no manifest and no other used script names, with what still names each (tests, documents, another script). It only reports: nothing is deleted anywhere. With tests; the generated `docs/VENDORED_TOOLS_REPORT.md` can be written again at any time.
- **Translations that fell behind are told section by section:** `python tools/readme_staleness.py [REPOSITORY ...] [--all]` asks `git blame` when each `## ` section of every README file was last written and says which sections of another language are older than the English one by more than a grace (24 hours by default). It is informative only (the exit code is always 0), it is a separate script and not part of `ci_validate.py`, so the shared validator does not change and nothing has to be carried to the other repositories. With tests.
- **The notes of a release and the check before publishing it:** `python tools/release_notes.py REPOSITORY [VERSION]` prints the title and the notes of a release (the section of that version of the CHANGELOG, ready for `gh release create --notes-file`; `--title` and `--notes` print one of them), and `--check` fails when the CHANGELOG has no section for the version of the manifest or `[Unreleased]` still holds entries (fewer than 3 entries is a warning with its own exit code, accepted with `--allow-short`). `python tools/prerelease_check.py REPOSITORY` lists what has to be up to date before a release (the same version in every file, the CHANGELOG, the eight README files with the same status lights, a clean tree with nothing left to push, the repository's own `ci_validate` in PASS, and the GitHub Actions runs of the checked out commit when `gh` is installed, saying so when it is not); it publishes nothing. With tests.
- **One command raises the version of a repository everywhere:** `python tools/bump_version.py REPOSITORY NEW "Title"` writes the new version in the manifest, `Cargo.toml` and `Cargo.lock`, `package.json` and `package-lock.json`, `pyproject.toml` and the `__version__` mirror, the Gradle files (`versionName`, and `versionCode` + 1), `project.yml` (`MARKETING_VERSION`, and the build number + 1), the file named by `native_version`, the badge and the table of the eight README files, and turns the `[Unreleased]` entries of the CHANGELOG into the section of the new version. It accepts only the version the odometer gives (every number goes from 0 to 9 and carries to the one before: 0.0.9 to 0.1.0, 0.7.9 to 0.8.0.0) unless `--explicit` is given, refuses to start when a file that should carry the version is missing or holds another one, writes nothing with `--dry-run` (it shows the diff), keeps the CRLF or LF of each file, and ends by reading everything again and failing if any place differs from the manifest. With tests on toy repositories, among them one that pins that `package.json` and its lock follow the manifest.
- **One validator for the whole suite:** `tools/ci_validate.py` is now the superset of the variants the repositories had: it reads the native version where the manifest says (a single pattern or major/minor/patch/build patterns), checks the iOS `project.yml` when there is one, calls the status lights and the README layout check, and takes the data of a repository from an optional `tools/ci_config.json` (`skip_dirs`) instead of from edits to the code. Its header carries `# canonical: EH3D-DOCS tools N` and its last line is `CI_VALIDATION=PASS project=... version=... tools=N`. `sync_shared_tools.py --write` refreshes that header line in the copy it writes. With tests.
- **The suite contract checks the tools and uses the real parser:** the new `tools` check warns about every repository whose `ci_validate.py` is not the copy of this hub (or states another tools version), and the `manifests` check now also runs every manifest through the parser of EH3D-UPDATER when that repository is next to this one. With tests; both stay warnings or errors of the daily job only, never a blocking check.
- **The copies of the shared tools are compared:** `python tools/sync_shared_tools.py` says, for each tool that every repository carries (the validator, the status lights, the drawers of the pictures), how many different versions there are and which repositories differ from the one of this hub; `--check` fails when any does, and `--write --only TOOL --repo REPOSITORY` carries the canonical copy to one repository, keeping its own header. It never rewrites the whole suite at once. With tests.
- **The Release column of the map is written, not copied:** `python tools/suite_contract.py --write-map` puts the version of the manifest of each repository that is in the workspace in the Release column of `docs/SUITE_MAP.md` and changes nothing else of the map (the words are a person's), with a test; the check of the versions of the daily job tells which rows are behind.
- **The suite contract:** `tools/suite_contract.py` checks the relations between the repositories that none can check by itself (readable manifests that carry the name of their folder, a version next to every dependency by path, the versions of the map of the suite, the port of the server in the screens), with its tests; a daily workflow (`suite-contract.yml`) clones the repositories and lists what drifted. It only warns for now; the known exceptions are in `docs/suite_contract_allow.txt`.

## [0.0.4] - The matrix and the architecture with resuming and the GRBL switch

- **Going on from a stopped job, and the `$` lines of GRBL per machine:** the matrix and the architecture say that the server keeps the request of every job and makes a new, never started job from a stopped one with the work done left out, that the three clients use it, and that an administrator can allow the `$` lines of GRBL on one machine with a safety switch that is off by default.

## [0.0.3] - The map, the matrix and the architecture with G-code, GRBL and the new releases

- **Free G-code jobs, the GRBL connection and the programs that send their work to the server:** the map, the matrix and the architecture say that the server runs a program of G-code line by line on the simulator or on a GRBL controller, that it can be held, resumed and gone on from the line where it stopped, that the spindle and the coolant start again only when asked, that a node, a GRBL controller and the simulator take different kinds of job, and that the drilling, routing and machine control programs, Studio and the phone apps work with the server; the matrix has two new rows.

- **The Release column and the rows of the newest releases:** the map lists the release that is on GitHub for each repository (the Android and iPhone apps 0.0.3, the touch screens 0.0.4 and 0.0.2, the drill head node 0.0.5, the programs 0.0.9, the modern interface 0.1.5), what a release now holds is no longer said to be on the main branch, and the Android APK of 0.0.3 is said to have been tried on a phone.

- **The map with the release of each repository, and the newest work:** the map has a Release column; the map and the matrix say that the interfaces of the programs, the touch screens and the panel of the nodes speak 37 languages, that a Bungard machine has two spindles (60000 rpm the original one, 24000 rpm the one with a drive) with limits that the server enforces, that a job can be the drilling, the routing or both with any tool switched off, and what the sensors of the node of the drill head do (laser, several temperature sensors, a reflective speed sensor with a filter and the settings of the camera picture), each with what has not been tried on a real machine. The general purpose touch screen is described with its kind of machine, and the README in eight languages counts the twenty-seven published repositories.

- **The new programs are published:** the launcher, the tool crib, the isolation program, the laser program, the Gerber viewer, the stencil program, the levelling utility, the pick and place manager, the vision studio, the G-code debugger and the general purpose touch screen have their first release, so the map lists them as published.

- **The ring of LEDs and the quality check of the drill head:** two rows in the matrix (the ring of LEDs around the camera with its colour signals and the picture on request; the quality check of the holes and of the milled channels with one verdict) and a sentence in the map for each repository that has it. Both say what has not happened: no ring has been driven and no real board has been photographed.

- **The map, the matrix and the architecture for the programs that have started:** the launcher, the tool crib, the isolation program, the laser program, the Gerber viewer, the stencil program, the height-map program, pick and place, the debugger and the vision program have a line in the map as started (a library and a command line with tests, no release yet) and a row each in the matrix; the phone apps for Android and iPhone are listed as published; the catalogue of bits is more than 450 and the node of the drill head, the web panel of the nodes and the recovery of a program in MOTIONCNC are mentioned.

- **The node of the drill head through the server and in Studio:** the matrix and the architecture say that the server relays the node (`/api/v1/machines/:id/head/...`), that Studio shows it on the page of a machine, that the cameras are the OV2640 and the OV5640 and that the drivers of the sensors are written but have never run.
